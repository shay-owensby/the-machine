# GA4 reporting data contract

Use this contract for every report generated by the skill.

## 1. Data source and access

Google Cloud Console is the credential, project, and API-enablement layer. Report data and authoritative response metadata come from the Google Analytics Data API v1. The Google Analytics Admin API is optional and is used only for descriptive property metadata such as display name, property type, industry category, and service level.

Required inputs from the client project root:

- A numeric GA4 property ID, commonly stored as `GA4_PROPERTY_ID`, `GOOGLE_ANALYTICS_PROPERTY_ID`, or a clearly equivalent key in `./.env`.
- OAuth 2.0 credentials with `https://www.googleapis.com/auth/analytics.readonly`, using Application Default Credentials, a service-account credential whose identity has property access, an OAuth refresh-token flow, or an authorized access token.
- Viewer-or-higher access to the target GA4 property for the authenticated identity.

Inspect `.env` key names without revealing values. Accept the project's existing naming convention rather than rewriting `.env`. Common credential keys include `GOOGLE_APPLICATION_CREDENTIALS`, an inline or path-based service-account JSON key, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`, `GOOGLE_OAUTH_ACCESS_TOKEN`, and `GOOGLE_CLOUD_PROJECT`. An API key can associate quota with a Cloud project but does not by itself grant an identity access to private GA4 property data.

Do not source an untrusted `.env` as executable shell code. Use a dotenv parser or parse only simple key/value assignments. Never print variables, raw authorization headers, tokens, private keys, client secrets, or credential JSON. Do not persist raw responses containing user-level or sensitive dimension values.

Preferred endpoints:

- Core reports: `POST https://analyticsdata.googleapis.com/v1beta/properties/{property_id}:runReport`
- Batch reports: `POST https://analyticsdata.googleapis.com/v1beta/properties/{property_id}:batchRunReports`
- Metadata: `GET https://analyticsdata.googleapis.com/v1beta/properties/{property_id}/metadata`
- Compatibility: `POST https://analyticsdata.googleapis.com/v1beta/properties/{property_id}:checkCompatibility`
- Optional descriptive property metadata: `GET https://analyticsadmin.googleapis.com/v1beta/properties/{property_id}`

Use the newest stable or beta version supported by the installed official client library. Do not use alpha methods when a v1beta equivalent exists. Useful official references:

## 2. Fixed date convention

Use the GA4 property's reporting time zone and explicit ISO dates.

- Report date: calendar date on which the report is generated in the property time zone.
- Current period: the 30 complete calendar days ending yesterday, inclusive.
- Previous period: the immediately preceding 30 complete calendar days, inclusive.
- Both windows contain exactly 30 dates and never overlap.

Use named date ranges `current` and `previous`. When both appear in one `runReport`, the API adds a `dateRange` dimension. Do not include today unless the user explicitly requests partial-day data; then label the periods non-equivalent and do not represent the result as the default report.

First make the minimal Data API access and response-metadata probe defined in `ga4-query-plan.md`, using the relative date `yesterday`. Relative dates are interpreted in the property time zone. Read `metadata.timeZone` and `metadata.currencyCode` from the response, then convert the exact windows from `report_dates.py` into explicit ISO dates for every reporting query. Do not set a request `currencyCode` merely to discover the property currency, because a requested currency changes the response currency. Use the Admin API only when optional descriptive property metadata is useful. If the property time zone cannot be established, stop because the windows and output date cannot be guaranteed.

## 3. Required KPI catalog

The strict template is the canonical standard KPI catalog. Keep every row and query the corresponding Data API metric when it exists. Before querying, call `getMetadata` for the property so renamed, custom, unavailable, or blocked metrics are identified rather than guessed. Use each field's current `apiName`; do not rely on a deprecated alias. If MetricMetadata lists `blockedReasons`, label the metric `N/A — access restricted: <reason>`. A blocked metric can return zero, so never interpret that zero as observed performance.

Also include:

- Every property-specific custom metric that is both available in Metadata and meaningful enough to interpret, in **Property-Specific and Custom KPIs**.
- Every registered key-event-specific rate exposed by Metadata when it materially affects business outcomes, in **Key Event Performance**.
- User-supplied business KPIs when a defensible formula and source data exist.

"Complete KPI scorecard" means all canonical rows plus applicable property-specific KPIs, not an undifferentiated dump of every experimental or irrelevant metric in the API schema. Mark unsupported or inapplicable canonical rows `N/A — <reason>`; never remove them.

## 4. Normalization and calculations

Preserve full precision for calculations and round only for display.

- Fractions returned for rates: multiply by 100 for percentage display.
- Currency: use the property's ISO 4217 currency; do not mix event-local currencies without explicit conversion.
- Durations: display seconds and a human-readable duration when helpful.
- Counts: display whole numbers unless modeled values are fractional.
- Distinct-user metrics: use an unsegmented API total. Never sum them across dates, channels, pages, events, devices, or geographies.
- Active-user windows (`active1DayUsers`, `active7DayUsers`, and `active28DayUsers`) and stickiness ratios are rolling point-in-time values ending on the query's final date, not totals across the 30-day report window.
- Unique-user and session counts can use HyperLogLog++ estimation. Treat small differences as potentially approximate and disclose this when it affects a conclusion.
- Ratios and averages: prefer an unsegmented API total or recompute from compatible additive bases. Never average row-level rates.

| KPI | Formula or validation relationship |
|---|---|
| Engagement rate | engaged sessions / sessions |
| Bounce rate | (sessions - engaged sessions) / sessions; should complement engagement rate |
| Sessions per user | sessions / active users, using the API definition when totals differ |
| Events per session | event count / sessions |
| Event count per user | event count / active users |
| Views per session | screen/page views / sessions |
| Views per user | screen/page views / active users |
| Average revenue per user | total revenue / active users |
| Purchase-to-view rate | use the API metric rather than a naive event-count ratio |
| Cart-to-view rate | use the API metric rather than a naive event-count ratio |
| ROAS | total revenue / advertiser ad cost, only when attribution scopes are comparable |
| Cost per key event | advertiser ad cost / key events, only when scopes are comparable |

Period comparison:

- Absolute change = current - previous.
- Relative change = (current - previous) / previous.
- For rates, show percentage-point change as the absolute change and relative percentage change separately.
- If previous is zero and current is nonzero, relative change is `N/M — no prior-period base`.
- If both are zero, relative change is `0.0%`.
- If either period is unavailable, both change fields are `N/A`.

Direction is contextual. Higher users, engagement, key events, or revenue can still be poor when quality, profitability, or measurement deteriorates. Lower bounce rate, cost per key event, or refunds are generally favorable only when the scopes and data are comparable.

## 5. Query and pagination rules

- Reuse one authenticated client per API and one property-scoped Metadata response during a run.
- Use `runReport` for ordinary tables. A report request supports at most 9 dimensions and 10 metrics.
- Use `batchRunReports` only for independent requests against the same property, with no more than 5 report requests per batch. Batching reduces network round trips, but each contained Data API request still consumes quota.
- Name the ranges `current` and `previous`; keep filters, dimensions, metrics, currency, and attribution settings identical between them.
- Use `checkCompatibility` when testing uncertain fields or discovering compatible additions to an existing request. Supply the intended base dimensions, metrics, and filters; do not preflight every known-good family because compatibility calls consume quota too. Split incompatible fields into separate query families.
- Use the paired named ranges in one request where the fields are compatible. The API supplies a `dateRange` response dimension for the two periods.
- Make one or more dimensionless totals requests authoritative for the KPI scorecard. Do not derive those totals by summing segmented rows or by relying on aggregations from diagnostic tables.
- Paginate with explicit `limit` and `offset`. The default is 10,000 rows and the per-request maximum is 250,000. Continue with the same request shape and deterministic `orderBys` until collected rows reach `rowCount` or a page is empty.
- Request `returnPropertyQuota: true` on the access probe and on the first, high-cost, or final reporting request. Avoid needless high-cardinality combinations and do not retry repeated 500/503 responses aggressively.
- Keep `keepEmptyRows` false unless a specific diagnostic requires empty rows.
- Do not query realtime data for this historical report.

## 6. Reconciliation and data quality

Before analysis:

1. Confirm property ID, time zone, currency, and any optional descriptive metadata source.
2. Confirm both ranges contain exactly 30 complete dates.
3. Confirm paired queries use identical shapes and filters.
4. Reconcile core unsegmented totals with totals returned by major segmented reports.
5. Detect `(not set)`, `(other)`, blank, thresholded, and privacy-suppressed rows.
6. Inspect `samplingMetadatas`, `subjectToThresholding`, `dataLossFromOtherRow`, `schemaRestrictionResponse`, `emptyReason`, `currencyCode`, `timeZone`, and returned property quota. Do not report sampled, thresholded, access-blocked, or `(other)`-affected data as exact and complete.
7. Check tagging plausibility: sudden discontinuities, duplicate key events, self-referrals, unassigned traffic, missing landing pages, or revenue without purchases.
8. Distinguish `totalUsers`, `activeUsers`, and `newUsers`.
9. Distinguish session-scoped acquisition from first-user acquisition.
10. Treat attribution, modeled data, consent mode, late events, identity settings, and key-event registration dates as caveats when material.
11. Remember that adding dimensions can change aggregate metrics because rows lacking those dimensions may be excluded; compare like-for-like request shapes.
12. Account for data freshness and late event processing when the most recent complete days appear anomalous.

Investigate discrepancies that could change a conclusion. A difference above both 1% and a meaningful business amount is a useful review trigger, not an industry benchmark.

## 7. Analysis standards

Every executive conclusion must be traceable to evidence. Each strength or weakness should cite at least one KPI and one relevant channel, campaign, audience, page, event, device, or geography where possible.

Prioritize by business impact, confidence, controllability, and urgency. Recommendations must state the evidence, action, intended KPI movement, owner role, time horizon, and validation method. Do not promise exact uplift without a user-supplied forecast or experiment.

## 8. Output rules

- Follow `report-template.md` exactly: same headings, order, and canonical KPI rows.
- Replace every `{{PLACEHOLDER}}`; use `N/A — <reason>` rather than deleting content.
- Default top/bottom tables to 10 rows; use fewer only when fewer exist.
- Save to `./analytics-insights/google-analytics/YYYY/YYYYmmdd-google-analytics-report.md` using the report date in the property time zone.
- Save no raw credential material or user-identifying data.
- Validate with `scripts/validate_report.py` before delivery.
